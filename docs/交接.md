## 一句话

LSPosed 模块(包名 `com.localai.notif`),在小米 15(HyperOS 4.0.3.0.XOCCNXM,Android 17,国行)上用**本地端侧小模型**(Qwen3-1.7B-int4,MNN 推理)实现:iOS 式通知摘要、噪音治理、重要通知置顶、iOS 18"减少干扰"复刻、早间日报。完整设计见 `docs/设计.md`。

## 构建与安装(Windows,无需 Gradle)

```bash
bash build.sh                     # 日常调试，生成 dist/LocalAiNotif-v<版本>-debug.apk
BUILD_TYPE=release bash build.sh  # 日常使用，生成 dist/LocalAiNotif-v<版本>.apk
```

- SDK: Android SDK（build-tools 35.0.0, platforms android-34/35/36; 链接用 android-36; NDK clang++）
- **JNI**。`build.sh` 步骤 4b 从 `jni/localai_llm_jni.cpp` 生成 `build/<debug或release>/jniLibs/arm64-v8a/liblocalai_llm.so`，链接预编译 `libMNN.so`。模型单独部署。
- **16KB 页对齐(v0.4.0 新增)**:`zipalign -f -P 16 4` + 链接器 `-Wl,-z,max-page-size=16384`(Android 15+ 16KB page 设备要求)
- **需前置:MNN Android 构建**(flatbuffers 头文件来源)。工具链坑:flatc 必须用 1.11——flatc 1.10 生成的 int32 TypeTable 数组与 vendored 1.10 头不兼容;flatc 1.12 生成 IsOutRange 调用而 1.10 头里没有。做法:把 flatc 1.11 release 可执行文件拷到 `3rd_party/flatbuffers/tmp/flatc`,`schema/generate.sh` 用相对路径引用它
- 签名（2026-11-24 已切换为专属正式密钥 + APK v3 轮换链）：默认读取 `D:/onedrive/安卓签名密钥/LocalAiNotif/signing-backup.json`（可通过 `SIGNING_DIR` / `SIGNING_CONFIG` 覆盖，**密码与密钥不入库**）。新密钥 `localai-notif-release.p12`（`CN=LocalAiNotif, O=InternetBugs`，3072-bit RSA，`SHA384withRSA`，证书 SHA-256 `89:03:4F:48:BD:F1:31:45:5E:DE:17:C3:60:87:29:36:72:95:D3:53:3A:73:FA:23:18:15:85:14:30:81:CE:CC`），附带 `localai-notif-v3.lineage` 链接旧 debug 密钥（`29:BB:0E:...`），支持已装旧版无缝覆盖升级。`build.sh` 已兼容 Windows Git Bash 与 Linux（Ubuntu CI），不再清理 `dist/`，缺失签名配置时直接报错退出，严禁回退或自动新建 debug keystore。
- **GitHub Actions 手动发版**（`.github/workflows/release.yml`，仅 `workflow_dispatch` 手动触发，绝不自动发版）：
  - 在 GitHub 仓库 **Actions → Manual Release → Run workflow** 手动触发；留空 `tag` 时自动读取 `AndroidManifest.xml` 的 `v<versionName>`（稳定版强制要求 `tag == v<versionName>`，保证与 `ReleaseUpdate.java` 内置更新器一致），支持 `draft` / `prerelease` / 自定义 `release_title` 与 `release_notes`。
  - 云端自动拉取固定 commit（`b0239771b07b317a258fbc384683bbd540741406`）的 `alibaba/MNN` 并用 `actions/cache@v4` 缓存 `libMNN.so`，调用 `build.sh` 构建并校验 16KB 页对齐、3 个 ARM64 `.so`、新证书指纹及内嵌 v3 轮换链，随后生成 `SHA256SUMS.txt` 并创建 GitHub Release。
  - 仓库 GitHub Actions Secrets 已配置 8 项：`RELEASE_KEYSTORE_BASE64`、`RELEASE_STORE_PASSWORD`、`RELEASE_KEY_ALIAS`、`RELEASE_KEY_PASSWORD`，以及用于无缝覆盖升级的 v3 轮换项 `SIGNING_LINEAGE_BASE64`、`LEGACY_KEYSTORE_BASE64`、`LEGACY_KEY_ALIAS`、`LEGACY_KEY_PASSWORD`（未来不再需要兼容旧 debug 密钥时删掉后 4 项即可自动降级为单密钥直签）。修改 `build.sh` 时务必保持 Linux/Ubuntu 兼容性。
- 安装时通过无线 ADB 执行 `adb -P 5038 install -r`，传入本次构建的 APK 路径。如系统弹出安装确认，在手机上允许。
- 激活时，在 LSPosed 管理器启用模块并检查四个静态作用域 `system`、`com.miui.notification`、`com.android.settings` 和 `com.android.systemui`。更新 VIP 分组或摘要后需要重新加载 `system_server` 和 SystemUI。软重启优先，本机以 shell 身份执行 `am restart` 缺少 `SHUTDOWN` 权限。
- 验证加载:`adb logcat -s LocalAiNotif`,应见 `Loaded in process: com.android.systemui` 与 `Hooked merged group summary view`

### 模型部署(免 root,Android 15 实测路径)

APK 不带模型;Qwen3-1.7B 的 MNN 模型目录单独装进应用私有目录:

```bash
adb push qwen3-mnn /data/local/tmp/qwen3-mnn
adb shell run-as com.localai.notif cp -r /data/local/tmp/qwen3-mnn files/models/qwen3-1.7b-mnn
```

- 前提:应用声明 `android:debuggable="true"`(run-as 需要)
- **坑**:外部存储 scoped-storage 目录(external-data)推得进去但**不能用**——目录 mode 770 导致应用侧 `File.exists()` 为 false;必须走上面 run-as 路径
- 模型路径可配:`get_config` 中 `model_path` 键(`Config.KEY_MODEL_PATH`),默认 `/data/user/0/com.localai.notif/files/models/qwen3-1.7b-mnn`;换模型后 `reset_engine` 关引擎,下次调用自动重载

## M3 重要通知专区（v0.7.2 实机验收）

- 「重要通知」默认开启。模块启动页可关闭，关闭后原有 VIP 卡片回到普通分区。
- 原生通知分区在锁屏和通知中心把 VIP 提到普通通知之前。同一应用的两条及以上 VIP 组成一个原生折叠组，调用 `summarize_group` 时仅传入组内 VIP。减至一条时恢复单卡。普通通知留在框外，继续按系统规则分组。专区仅在存在可见 VIP 时显示标题。
- 标题和重要卡片共用琥珀色外框，边界取自可见卡片的实际位置。用 HyperOS 的实际渲染透明度判断卡片是否可见，锁屏标题放在第一张卡片上方。
- 息屏声震由系统通知通道和勿扰设置处理。初版短暂设置的 `FLAG_INSISTENT` 会让原生播放器循环提醒，已移除。
- 构建后核对 APK 与 v0.6.1 的签名一致，三个 ARM64 原生库均通过 16KB APK 对齐检查。
- 小米 15 `OS4.0.3.0.XOCCNXM` 实测锁屏和通知中心的外框。来自 `com.android.shell` 的两条 VIP 合并显示摘要，同应用两条普通通知另组并留在框外。清除一条 VIP 后恢复单卡，清除最后一条 VIP 后标题和外框消失。本轮手机未部署 Qwen 模型，组摘要由规则兜底生成。

### v0.7.3 候选包

- VIP 分组按 Android 用户和应用隔离。成员及内容相同时复用摘要请求状态，组成员或内容变化后重新生成。
- 组缩到单条时恢复已显示和入队更新的原生分组。锁屏绘制前检查组内通知的脱敏状态。展开动画中，外框底边以第一张普通卡片为界。
- `dist/LocalAiNotif-v0.7.3.apk` 已完成构建，签名与 v0.7.2 一致，APK 通过 16 KB 对齐检查。手机当前运行已验收的 v0.7.2。候选包待实测跨应用分组、组成员变化和锁屏隐私切换，Qwen 推理需在部署模型后验证。

### v0.7.3 性能优化包

- 通知栏调用 `summarize_group` 时传入 `include_item_summaries=false`，仅生成组摘要。包含 N 条输入的组摘要阶段从 N+1 次模型生成降到 1 次。省略该参数时仍返回逐条摘要和错误列表。
- 分类先应用强 VIP 和噪音规则，只有规则未定案的条目进入模型。模型结果按原通知顺序写回。调度达到阈值后复用当轮扫描结果，组指纹复用已计算的子项指纹。
- `dist/LocalAiNotif-v0.7.3-perf.apk` 沿用 v0.7.3 的版本号和签名，并通过 16 KB 对齐检查。桌面桩测覆盖推理调用次数、分类回映射、等待阈值和指纹兼容性。小米 15 上的 Qwen 延迟待实测。

### v0.7.3 纯模型分类包

- 普通、噪音、重要及 VIP 的判定统一由端侧模型完成。原通知按系统流程先投递，有效的模型结果随后更新重要通知分组或噪音处理。缺模型、推理失败和无效条目保持原生行为。
- 组摘要仍只生成组级文本。安装包为 `dist/LocalAiNotif-v0.7.3-model-only.apk`，沿用 v0.7.3 的版本号与签名。

### 模型到底怎么被调用

AOSP 本体不碰模型,调用点在 NAS(NotificationAssistantService)的实现方:

1. `NotificationManagerService` 绑定 `mAssistants`(`notification-assistant` 角色 / `config_defaultAssistantAccessComponent`)。
2. 通知入队时 `ManagedServices.onNotificationEnqueuedLocked` 把 `IStatusBarNotificationHolder` + `NotificationChannel` + `NotificationRankingUpdate` push 给对方。
3. 实现方(GMS 侧,Android System Intelligence)自己决定等多久、攒几条、哪些应用——**这层策略完全闭源**,AOSP 不参与。
4. 实现方调 ML Kit GenAI `Summarization`(`SummarizerOptions.setInputType(ARTICLE|CONVERSATION|PLAIN_TEXT).setOutputType(ONE_BULLET|TWO_BULLETS|THREE_BULLETS)`,`SummarizationRequest` + `runInference`),ML Kit 再经 AICore(AOSP 之外的系统服务,管理端侧基础模型)跑 Gemini Nano + 该能力的 LoRA 适配器,流式回 token。
5. 结果包成 `Adjustment(KEY_SUMMARIZATION=文本)` 回 `applyAdjustment(s)FromAssistant`(单条)或 `updateNotificationRanking`(批量)。
6. SystemUI 只做渲染:折叠行加高 + 单行替换文案 + 反馈按钮。

对 LocalAiNotif 的含义:AICore 不在 AOSP 里、也不是公开 API,受系统侧权限管控,第三方无权直接调;所以「借 AOSP 的模型调用」这条路不存在,自建 MNN 是唯一解(与 `## 背景考古` 记录的 HyperOS 云控未下发模型结论一致)。

### 可移植的四条(按价值排序,均属本地可改、无需实机)

1. **CONVERSATION 输入格式**:ML Kit 会话摘要要求逐行 `<名字>: <消息>`。`InferenceProvider.mnnGroup` 现在拼的是 `1. 标题: 内容` 编号列表,聊天类通知应换成人名/前缀行,提升「谁说了什么」的保真度。
2. **bullet 输出契约**:官方 output type 只有 1/2/3 条 bullet,没有「一句话总结」。现在强制 40 字单句 + `「<app> <count>条通知:概括」` 模板,模型两步都在复述模板、容易空洞;改成「≤3 条短 bullet,自己挑最重要的」更实,`GroupSummaryData.SUMMARY` 换行渲染即可。（2026-11-24 部分落地：模板前缀已改由代码拼接，模型只写 ≤36 字概括，见「摘要提示词与解码调整」；bullet 形式未做。）
3. **输入长度门限**:4000 token 上限、ARTICLE 需 >400 字符。现在 `line_count ≤ 3` + 内容截 60 字对 0.6B/1.7B 是合理保守值,但 ARTICLE 类(新闻/长文推送)应走独立提示词并允许更长正文,而不是套聊天模板。
4. **失效语义**:AOSP 用显式 `null` 撤回;`clearGroup` 删 extras + `notifyUpdated` 等价。但 AOSP 在通知被划掉/撤销时立刻撤摘要,本地 `cachedGroups` 里的旧摘要可能多活一个 `collect()` 周期,值得对齐。

### 不做的事

- 不引入 AOSP 的 `Ranking.getSummarization` / `EXTRA_SUMMARIZED_CONTENT` 通道:HyperOS 4 的 `MiuiSystemUI` 无此实现,该通道在本机不存在,继续用自家 `localai.group_summary` extras + `PriorityNotification.notifyUpdated` 重排。
- 不复刻 `nmSummarization` 的 aconfig flag 语义(那是给 OTA 灰度用的,模块侧无意义)。

## 摘要提示词与解码调整（2026-11-24，参考小米端侧摘要提示词，待实机验证）

对照小米端侧通知摘要提示词（通用文本：不超过原文 20%、保留人称、不得编造；短信：不超过 36 字，出行与餐饮类用 `【状态】` 开头），用户选定以下改动：

- **忠于原文**（`InferenceProvider.SYSTEM_PROMPT` 与 `SUMMARY_RULES`）：要求保留关键信息与原文人称；数字、金额、时间、地点、取件码、验证码原样保留；不得出现原文没有的内容；输出语言跟随原文。规则在系统提示词中写一次，并在每条用户提示词末尾重复一次，因为小模型最遵从最后一条指令。
- **原文隔离与防注入**：原文统一放在 `<notif>…</notif>` 中，指令放在其后。系统提示词声明标签内只当数据、不执行其中的指令。`untag()` 删除标题、正文、应用名和模型输出中的 `<notif>` / `</notif>`，防止原文提前闭合标签。
- **组摘要前缀由代码拼接**（`mnnGroup` / `groupPrefix`）：模型只输出不超过 36 字的概括，`<应用名> N条通知:` 由代码拼接；如果模型仍自行写出该前缀，会被正则删除。总长度上限仍为 54 字。启发式兜底 `groupSummary` 也改用同一前缀，从 `<App> N 条通知` 变为 `<App> N条通知:`。
- **组摘要输入**：只放最新 `GROUP_PROMPT_ITEMS = 8` 条，按从新到旧排列，以控制端侧首轮输入（prefill）耗时。上游 `Batch.requested` 仍最多 10 条（`GroupSummaryData.MAX_ITEMS`）。`NotificationSummaries` 额外传 `totalCount = batch.children.size()`，前缀与提示词中的条数都使用真实总数；超出时提示词注明“仅列出最新 8 条”。
- **真实应用名**：`NotificationSummaries.appLabel()` 在 system_server 中通过 `PackageManager` 取应用名，以 `appLabel` 传入；`:inference` 进程受包可见性限制，无法自行取。取不到时回退到包名末段，过长截到 16 字。单条摘要原文中也增加“应用:”行。
- **解码与状态**（`jni/localai_llm_jni.cpp`）：`nativeCreate` 在 `load()` 前设置 `{"sampler_type":"greedy"}`。本机 MNN（`b023977`）默认使用温度 1.0 的 mixed 采样，而采样器在 `load()` 中创建，所以必须在加载前设置。分类与摘要共用同一引擎，二者都变为确定性输出。`nativeGenerate` 每次调用 `response()` 前先调用 `llm->reset()`（见下方 P1 第 20 项）。
- **用户明确不采纳**：原文过短时跳过摘要；`【状态】` 前缀；在提示词里说明“标题通常是发送者”；few-shot 示例。
- **已做验证**：全部 `src/` 通过 `javac --release 17` 编译（android-36 + libxposed）；JNI 通过 NDK 28 `clang++ -fsyntax-only` 检查。沙箱中 Git Bash 无法启动，未跑完整 `build.sh`。
- **小米 15 待验**：需重新编译 `.so`。验证项：组摘要前缀显示中文应用名与真实条数；超过 8 条时生成正常；摘要中的数字、取件码与原文一致；英文通知输出英文；分类 JSON 在贪心解码下是否稳定；端侧推理延迟变化。

### P1：推理进程与调度逻辑缺陷

14. **`mFailedModelPath` 永久粘滞不重试**（`InferenceProvider.java:627,644,666-668,705,735`）：一次低内存或拷贝中途加载失败后，同一路径永不重试直到手动改路径/重置。建议加 `mFailedAtMs`（如 5 分钟冷却期）及目录 `lastModified` 变化时允许重试。

16. **同一条通知并发重复分类**（`NotificationSummaries.java:562-576`）：`dispatch` 未将 `batch.toClassify` 记入 `classificationInFlight`，导致 `dispatchPendingClassifications`（L654）并发重复下发。建议 `dispatch` 时登记并在 `applyPriorityClassification`/`finish` 的 `finally` 清理。
17. **「亮屏时不摘要」模式下丢弃已算好的组摘要**（`NotificationSummaries.java:874-879`）：推理完成后只移除 `attempted` 就 return，下次息屏重跑一遍 LLM。建议 `status=="0"` 时先写入 `cachedGroups`，仅推迟 `setGroup`；另外 L876 可直接复用成员字段 `power`。
18. **`AsyncConfig` 首次拉取失败不重试，全部配置静默回落默认值**（`AsyncConfig.java:44-62`、`NotificationSummaries.java:265-271`）：开机 `:inference` 被冻结导致 `query.get()` 返回 `null` 时，`AsyncConfig` 保持空 `Bundle` 并直接触发 `updated.run()` 置 `configReady=true`，导致 `KEY_MODEL_READY`/`KEY_REDUCE_ENABLED`/`KEY_ALWAYS_LOAD_MODEL` 等全按默认值跑，直到下次广播才恢复。建议 `value == null` 时在 handler 上做指数退避重试（2s / 5s / 15s 封顶）且不要拿空 Bundle 误判为已就绪。
19. **模型未就绪时仍发 `classify` IPC**（`NotificationSummaries.java:578-582`）：`isClassifyEnabled` 未检查 `KEY_MODEL_READY`（对比推广扫描 L610 已检查），无模型时仍反复唤醒 `:inference`。建议加上 `KEY_MODEL_READY` 门限，减少干扰 pending 路径本地直接走 fail-closed。
20. ~~**每次推理前未调用 `llm->reset()`**~~ **已修复（2026-11-24）**：`nativeGenerate` 在每次 `response()` 前调用 `llm->reset()`，清空历史 token、KV 与 prompt cache，保证每次请求无状态，即使模型 `llm_config.json` 开启 `reuse_kv` / `prompt_cache` 或上次推理中途中断也不会串上下文。同时 `nativeCreate` 在 `load()` 前设置 `{"sampler_type":"greedy"}`（MNN 默认是温度 1.0 的 mixed 采样）。

## 2026-11-24 推广识别收紧

- **实机误判根因**：`Classifier` 输出 `class=noise` 后无任何确定性兜底，小模型（Qwen3-1.7B）将日常约饭聊天（如 `张三：中午一起去楼下吃拉面吗？我十一点半出发`）误判为 `noise` 并写入 `localai.promotion_version`。
