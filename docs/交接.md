## 构建与安装(Windows,无需 Gradle)

```bash
bash build.sh          # 用 Git Bash 构建，产物为 dist/LocalAiNotif-v<版本>.apk，模型单独部署
```

- SDK: Android SDK（build-tools 35.0.0, platforms android-34/35/36; 链接用 android-36; NDK clang++）
- **JNI(v0.4.0 新增)**:`jni/localai_llm_jni.cpp` → `build/jniLibs/arm64-v8a/liblocalai_llm.so`,链接预编译 `libMNN.so`(4,179,792 B);build.sh 步骤 4b 编译
- **16KB 页对齐(v0.4.0 新增)**:`zipalign -f -P 16 4` + 链接器 `-Wl,-z,max-page-size=16384`(Android 15+ 16KB page 设备要求)
- **需前置:MNN Android 构建**(flatbuffers 头文件来源)。工具链坑:flatc 必须用 1.11——flatc 1.10 生成的 int32 TypeTable 数组与 vendored 1.10 头不兼容;flatc 1.12 生成 IsOutRange 调用而 1.10 头里没有。做法:把 flatc 1.11 release 可执行文件拷到 `3rd_party/flatbuffers/tmp/flatc`,`schema/generate.sh` 用相对路径引用它
- 签名:debug keystore(`~/.android/debug.keystore`)
- 安装时通过无线 ADB 执行 `adb -P 5038 install -r`，传入本次构建的 APK 路径。如系统弹出安装确认，在手机上允许。
- 激活时，在 LSPosed 管理器启用模块并检查四个静态作用域 `system`、`com.miui.notification`、`com.android.settings` 和 `com.android.systemui`。更新 VIP 分组或摘要后需要重新加载 `system_server` 和 SystemUI。软重启优先，本机以 shell 身份执行 `am restart` 缺少 `SHUTDOWN` 权限。
- 验证加载:`adb logcat -s LocalAiNotif`,应见 `Loaded in process: com.android.systemui` 与 `Hooked merged group summary view`

### 模型部署(免 root,Android 15 实测路径)

APK 不带模型;Qwen3-1.7B 的 MNN 模型目录单独装进应用私有目录:

```bash
adb push qwen3-mnn /data/local/tmp/qwen3-mnn
adb shell run-as com.localai.notif cp -r /data/local/tmp/qwen3-mnn files/models/qwen3-1.7b-mnn
```

- 前提:应用声明 `android:debuggable="true"`(run-as 需要)
- **坑**:外部存储 scoped-storage 目录(external-data)推得进去但**不能用**——目录 mode 770 导致应用侧 `File.exists()` 为 false;必须走上面 run-as 路径
- 模型路径可配:`get_config` 中 `model_path` 键(`Config.KEY_MODEL_PATH`),默认 `/data/user/0/com.localai.notif/files/models/qwen3-1.7b-mnn`;换模型后 `reset_engine` 关引擎,下次调用自动重载

- 「重要通知」默认开启。模块启动页可关闭，关闭后原有 VIP 卡片回到普通分区。

## 噪音折叠"更多通知":已暂停的攻坚记录(2026-11-23,用户决定先不做)

**目标**:noise 类通知不仅静默,还要收进 HyperOS 原生"更多通知"折叠区。

**反编译已确证的机制**(本机反编译对照):
1. 入口卡聚合判据(MiuiSystemUI FoldNotifControllerImpl.sendFoldNotification:311)= `notification.extras.getBoolean("miui.unimportant")`——只看 extras,**不依赖任何 SystemUI 内存字段**。system_server 侧 `NotificationSummaries.muteNoise()` 打这个 extras 标志即可触发(02:36 实测:入口卡 `0|com.android.systemui|…|UNIMPORTANT|1000` 被原生 post 出过一次)。
2. 主列表折叠判据(FoldCoordinator$foldFilter$1.shouldFilterOut:117)= MIUI 扩展字段 `ExpandedNotification.mIsFold`——只存在于 SystemUI 进程内存,system_server 无法置位;置位途径 `NotificationUtil.setFold(entry, z)`(com.android.systemui.statusbar.notification.utils)。
3. sendFoldNotification 的触发源是 FoldCoordinator 的 NotifCollectionListener 回调(deBounce 100ms)与 UI 模式/密度变化回调(后者不带 shouldShow 门)。

**v0.6.0 两轮 LSPosed hook 均装上但零命中,xp 侧结论(关键事实)**:
- `FoldCoordinator$foldFilter$1.shouldFilterOut` hook:attach 成功(LSPosedFramework 日志-confirm),通知到达/更新/亮屏/shade 展开,**探针零调用** → 该 filter 在本机管线里不跑。
- `NotificationUtil.setFold` hook(反编译显示 collectionListener 每条 add/update 必调):同样 attach + `setFold resolved=true`,探针零调用 → collectionListener 路径在本机不执行。
- → 本机 SystemUI 的 FoldCoordinator 管线集成是死的(疑似 AOSP 新管线被 MIUI 关闭,sendFoldNotification 用 pipeline.getAllNotifs 拿数据但 coordinator 的 filter/listener 未挂);入口卡只在 UI 模式事件时被动 post,无持续事件源。

### 模型到底怎么被调用

AOSP 本体不碰模型,调用点在 NAS(NotificationAssistantService)的实现方:

1. `NotificationManagerService` 绑定 `mAssistants`(`notification-assistant` 角色 / `config_defaultAssistantAccessComponent`)。
2. 通知入队时 `ManagedServices.onNotificationEnqueuedLocked` 把 `IStatusBarNotificationHolder` + `NotificationChannel` + `NotificationRankingUpdate` push 给对方。
3. 实现方(GMS 侧,Android System Intelligence)自己决定等多久、攒几条、哪些应用——**这层策略完全闭源**,AOSP 不参与。
4. 实现方调 ML Kit GenAI `Summarization`(`SummarizerOptions.setInputType(ARTICLE|CONVERSATION|PLAIN_TEXT).setOutputType(ONE_BULLET|TWO_BULLETS|THREE_BULLETS)`,`SummarizationRequest` + `runInference`),ML Kit 再经 AICore(AOSP 之外的系统服务,管理端侧基础模型)跑 Gemini Nano + 该能力的 LoRA 适配器,流式回 token。
5. 结果包成 `Adjustment(KEY_SUMMARIZATION=文本)` 回 `applyAdjustment(s)FromAssistant`(单条)或 `updateNotificationRanking`(批量)。
6. SystemUI 只做渲染:折叠行加高 + 单行替换文案 + 反馈按钮。

对 LocalAiNotif 的含义:AICore 不在 AOSP 里、也不是公开 API,受系统侧权限管控,第三方无权直接调;所以「借 AOSP 的模型调用」这条路不存在,自建 MNN 是唯一解(与 `## 背景考古` 记录的 HyperOS 云控未下发模型结论一致)。

### 可移植的四条(按价值排序,均属本地可改、无需实机)

1. **CONVERSATION 输入格式**:ML Kit 会话摘要要求逐行 `<名字>: <消息>`。`InferenceProvider.mnnGroup` 现在拼的是 `1. 标题: 内容` 编号列表,聊天类通知应换成人名/前缀行,提升「谁说了什么」的保真度。
2. **bullet 输出契约**:官方 output type 只有 1/2/3 条 bullet,没有「一句话总结」。现在强制 40 字单句 + `「<app> <count>条通知:概括」` 模板,模型两步都在复述模板、容易空洞;改成「≤3 条短 bullet,自己挑最重要的」更实,`GroupSummaryData.SUMMARY` 换行渲染即可。
3. **输入长度门限**:4000 token 上限、ARTICLE 需 >400 字符。现在 `line_count ≤ 3` + 内容截 60 字对 0.6B/1.7B 是合理保守值,但 ARTICLE 类(新闻/长文推送)应走独立提示词并允许更长正文,而不是套聊天模板。
4. **失效语义**:AOSP 用显式 `null` 撤回;`clearGroup` 删 extras + `notifyUpdated` 等价。但 AOSP 在通知被划掉/撤销时立刻撤摘要,本地 `cachedGroups` 里的旧摘要可能多活一个 `collect()` 周期,值得对齐。

### 不做的事

- 不引入 AOSP 的 `Ranking.getSummarization` / `EXTRA_SUMMARIZED_CONTENT` 通道:HyperOS 4 的 `MiuiSystemUI` 无此实现,该通道在本机不存在,继续用自家 `localai.group_summary` extras + `PriorityNotification.notifyUpdated` 重排。
- 不复刻 `nmSummarization` 的 aconfig flag 语义(那是给 OTA 灰度用的,模块侧无意义)。

## 排障实记(v0.3.1 重启验证中遇到的假警报)

## 行为边界(诚实说明)

- 启发式摘要是**截断型占位**,非真摘要(v0.3.1 说明,历史保留);v0.4.0 起 MNN 正常时为 LLM 真摘要,模型缺失/引擎失败/LLM 空输出才回落启发式(v0.3.1 同款逻辑属预期行为)

## 背景考古(为什么必须自己做本地模型)

- 原生链路实机打通过:HNMS(system_server)→OpenCapabilityProvider→aicr LLMServiceImpl→Taiyi 创建能力→com.xiaomi.aiservice 端侧模型;仅两个软门槛都在 settings:`ai_notification_setting`(system)=1、`MIAI_LLM_Cloud_Control`(global)=`support,true|ram,8|MIAI,0`;均已实测绕过、且**测后已恢复原值(全部 delete 回 null)**
- 挡死的是第三道:服务器未向本机发布任何端侧 LLM(`getAIConfig creation/llm/vlm/mimo_dev → []`,模型管理页"关联服务"为空)。模型权重无法伪造 → 只能自建
- 上述实测的 logcat 证据、uiautomator 截图流程、模型管理页 UI 树均已在当时会话核过;云控 value 格式为 `support,true|ram,8|MIAI,0|x,9`(`\|` 分节、`,`分键值、长度必须恰 2、null 即空表 fail-closed)

### Google 侧端侧模型调研(2026-11-24 实机核验,结论:不可替代自建 MNN)

- **Pixel「AI Notification Summaries」功能本身**:闭源系统实现(Android System Intelligence + NAS 槽位 + Gemini Nano),仅 Pixel 9/10 且仅英文长会话,无对外 API,本机不存在可 hook 的组件。
- **底层模型公开调用路径(ML Kit GenAI,已 GA)**:Xiaomi 15 已进官方 Summarization/文本任务支持列表(https://developers.google.com/ml-kit/genai),但有四道墙:① AICore 仅允许**前台应用**推理,前台服务都不行,否则 `BACKGROUND_USE_BLOCKED`——`:inference` 后台进程被 system_server 拉起响应通知,永远吃这条,设计性排除,非工程可绕;② AICore 按 app 限流(`BUSY`/日电量配额),通知风暴不可控;③ Gemini Nano 权重不公开下载,仅经 AICore 私有目录+私有格式(基础模型+LoRA 分发),无转 MNN 工具且许可禁提取;④ ML Kit SDK 需 AAR/Gradle,违反本仓库纯 javac 约束
- **实机三层核查(小米 15 国行 `OS4.0.3.0.XOCCNXM`,无线 adb)**:`com.google.android.gms` 已装(第一层 ✅);`com.google.android.aicore` 未安装、`com.google.android.as` 未安装(第二三层 ✗);`am start -a android.settings.AI_SETTINGS` → Activity not started/conflict;Play 商店 `com.android.vending` 未装,`market://details?id=com.google.android.aicore` 只弹 ResolverActivity——AICore 均需自装 APK,模型下发仍受 Google 云控,与小米原生链路被云控挡死同构
- **「想要谷歌模型」的唯一合法等价物是 Gemma 开源权重**(Gemini 家族开放分支,MNN 官方已有转换包,可走现有 model_path + reset_engine 热切换):`taobao-mnn/gemma-3-1b-it-qat-q4_0-gguf-MNN`(1B QAT 端侧版,体积最接近现有档)、`taobao-mnn/gemma-4-E2B-it-MNN`(更强,内存高于 1.7B 档)。取舍:中文(尤其 1B 档)预期弱于 Qwen 中文专精系列,未实测,用户尚未决定是否加进 `ModelCatalog`

## 环境速查(Windows 坑)

- Git bash PATH 经常整个被清空:用绝对路径 `"/c/Program Files/Git/usr/bin/ls.exe"`、`/d/Python312/python.exe`、`/d/Android/Sdk/...`

## 不再改写系统 `ai_notification_setting`(模块开=运行时虚拟开启)

- **旧行为**:`hookSystemServer` 的 `HNMS.init` 拦截里 `Settings.System.putInt(...,"ai_notification_setting",1)`;模块停用/卸载后该值留在系统里,Settings 显示"AI 通知"开着但没有任何总结——污染用户环境
- **新行为**:删除该写入。真实设置值由用户自己决定,模块在运行时用 hook 虚构"开启":
  - system_server:`HNMS.init` 之后的 `mNotificationEnabled=true` 保持(原逻辑),故 `HNMS$1.onReceive` / `AISwitchContentObserver.onChange` 读到的开关状态与原生一致。`mNotificationEnabled` 全库只有这两处读,均已覆盖/无需落盘
  - `com.miui.notification`:`SystemUtils.isAiNotificationSettingOn(Context)→TRUE`(设置页开关与其 ContentObserver 的读数),`SystemUtils.updateAiNotificationSetting(Context,int)→不写`(设置页 toggle、`AccountReceive` 账号登录、`DownloadModelCompletedReceiver` 都不再落盘)
- **实机取证**(小米 15,HyperOS 4.0.3.0):`ai_notification_setting+NUL` 全 dex 精确扫描,`MIUINotificationCenter.apk classes.dex` 仅 2 处 → 正是上述两个 `SystemUtils` 方法,`Settings.apk` **0 处**,`MiuiSystemUI.apk` 1 处仅在 `SystemUIStat.trackSettings` 埋点,`/system/framework/services.jar` 0 处。故 hook 这两个方法即完整覆盖读/写面,不需要广谱 `Settings$System.getInt` hook
- **升级清理**:本机若已被旧版本写过 `1`,执行一次 `adb shell settings delete system ai_notification_setting`,之后模块不再写入
